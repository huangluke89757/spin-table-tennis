二、逐项走查（四段式）

① 结算页按钮不在首屏

潜在痛点 / 逻辑漏洞

手机横屏可视高度仅 320～430px，而结算页纵向堆叠了：品牌行 → 副标题 → 新纪录徽章 → 本局结果 → 结束原因 → 模式标签 → 进步幅度 → 失败构成（1 行摘要 + N 行条形）→ 历史十局（10 行）→ 按钮行 → 辅助面板开关 → 提示语，总高约 700～900px。按钮被压到折叠线以下，玩家必须滑动才能点到「再来一局」。

致命处在于：这个滑动动作本身会触发问题 ③（画面被切出 / 触发下拉刷新），于是「想再来一局」变成了「可能退出游戏」。这属于 RPT_028 所指的「把关键操作推入非首屏」的变体——不是把信息塞进弹窗，而是把按钮推进了滚动区。

适用设计原则

关键操作常驻（Pin Key Action）——用户在当前页面最想完成的那一个动作，必须在任何窗口尺寸下无需滚动即可点击。扫描流与深度流分流——「再来一局」属于决策后的立即动作（短心流），明细属于复盘阅读（长心流），两者应占据不同的空间层级，而不是在同一条纵向轴上排队。

黄金修改建议（两方案，见第三节草图）

方案 A · 左右分栏：左栏固定 240px 承载结果 + 两个按钮（不滚动），右栏独立滚动放「最近 10 局」明细。
方案 B · 底部固定操作栏：明细折叠成一行，展开后在按钮条上方的独立区域内滚动；按钮条贴底常驻。

异常分支 / 闭环检查点

· 历史记录不足 10 条（新用户第 1 局）时，右栏 / 展开区的空态是否友好？
· 窗口高度进一步压缩到 280px（横屏 + 浏览器工具栏全开）时，左栏与底栏是否仍完整可见？
· 右栏内部滚动到底后继续滑动，是否会冒泡到外层导致整页位移？需 overscroll-behavior:contain。

② 辅助面板侵占击球走廊

潜在痛点 / 逻辑漏洞

左下「正手 / 辅助关 / 拍面中立」面板与右下「音效 开 + 音量条 + 收起辅助」面板，同时占据屏幕底部两个角。第一视角下，球飞抵身前时的击球点光环恰好在屏幕下方中央偏左——左下拍面栏与它直接重叠，玩家是「看着球被面板盖住」在打球。

更根本的问题：这两个面板是常驻信息，而它们的实际查看频率极低（音效设置一局最多调一次，拍面栏读数在熟练后不再需要）。常驻低频信息占据了高频视线区域，属于 RPT_020 说的「信息过载挤占主操作区」。

适用设计原则

渐进式披露——默认只暴露必需，其余按需展开。信号与噪音比——对局中的视觉预算应优先给球、来球轨迹与击球点，UI 元素必须让路。预注意属性——需要被瞬间捕捉的是球的位置，而不是音量条。

黄金修改建议

1. 对局中默认收起辅助面板，仅保留右下角一个 28×28 的极简「⌃ 辅助」按钮（半透明，1.5s 无操作自动降到 0.35 透明度）。
2. 拍面栏改为击球瞬间的浮出条：只在击球后 800ms 内于底部中央淡入，显示「正手 · 拍面中立」，随后自动消失——从常驻面板变成即时反馈。
3. 音量条移入暂停页（暂停时本来就有足够空间），对局中只留静音 toggle。

异常分支 / 闭环检查点

· 新手第一局若默认收起，是否会因为看不到拍面提示而学不会？建议首次进入的前 3 局默认展开，之后自动收起并提示一次「已收起辅助面板，按 H 可随时展开」。
· 收起后的展开按钮与既有触摸控制簇（暂停 / 重开 / 辅 / 反）位置是否冲突？需做两两求交硬断言。

③ 滑动切出画面 / 无全屏

潜在痛点 / 逻辑漏洞

移动端浏览器中，从屏幕上滑会拉起系统导航条、下拉会触发刷新，两者都会让游戏画面被推出视口或直接中断对局。当前页面没有任何全屏或滚动锁定机制（代码中未出现 requestFullscreen）。触屏操作本身是高频大幅拖拽，误触概率极高。

适用设计原则

RPT_012 异常分支明确要求「移动端小屏需提供降级方案」——这里的降级就是：把「浏览器页面」升级为「应用视图」。心流保护——沉浸式游戏场地被系统手势反复打断，是对心流最直接的破坏。

黄金修改建议

1. 开始对局时请求全屏：在「开始对局」按钮的点击回调内（用户手势链内，否则被浏览器拒绝）调用 requestFullscreen()，并兼容 webkitRequestFullscreen（iOS Safari 仅 iPad 支持）。
2. 尝试锁定方向：全屏成功后调用 screen.orientation.lock("landscape")，用 try/catch 包裹——该 API 在 iOS Safari 上不支持，必然失败，失败时静默降级为现有的横屏引导层。
3. 兜底 CSS：对 html, body 设 overscroll-behavior:none; touch-action:none; height:100%; overflow:hidden，阻断下拉刷新与橡皮筋滚动；画布容器用 100dvh 而非 100vh，避免移动端地址栏收起时出现 60px 高度突变。
4. 提供右上角全屏切换按钮，让用户能主动退出全屏（否则全屏后无法返回）。

异常分支 / 闭环检查点

· 用户用 ESC 或系统手势退出全屏时，是否需要自动暂停对局？建议：退出全屏即自动暂停，否则玩家会在看不见完整画面的状态下继续失分。
· 全屏请求被拒绝（部分浏览器需二次授权）时，是否有可见的提示？建议静默失败 + 保持现有横屏引导层即可，但需在首次失败后不再重复弹权限询问。

三、两套结算页草图（供确认）

方案 A · 左侧固定结果 + 右侧滚动明细

左栏 = 结果 + 按钮（固定不动）　|　右栏 = 最近 10 局明细（独立滚动）

优点：横向利用 16:9 屏幕的富余宽度，纵向压力彻底解除；「本局结果」与「历史对比」并排，可横向扫读，信息密度反而提升；并列名次用「4、4」表达也更自然。

代价：需要改造结算页为 flex 双栏，左栏固定宽度在极窄横屏（如 640px 宽）下需降级为 200px；练习模式右栏需补内容（见问题 ⑧）。

方案 B · 底部固定操作栏 + 折叠明细

结果区（含折叠明细）在上方滚动　|　按钮条贴底常驻，不参与滚动

优点：改动面小于方案 A（结算页仍保持纵向结构，只是把按钮行抽出为固定底栏 + 明细加折叠）；默认状态下详情收起，首屏更干净，符合渐进式披露；对 640px 宽的极窄横屏更友好。

代价：「最近 10 局」默认不可见，原有的「一眼看到自己历史排名」的价值被削弱一次点击；折叠态需额外的展开/收起状态管理。

我的建议：选方案 A

理由是它同时解决了问题 ①、⑥、⑧ 三项——横向分栏天然适合「本局 vs 历史」的并列对比（RPT_023 同比分析的思路），并列名次在左右对照下也更容易读懂；并且它把纵向压力一次性清零，后续再往结算页加内容（如本周趋势、好友对比）不会再复发这个问题。方案 B 的折叠只是把压力推迟，明细一展开，问题 ① 会以另一种形式回来。

若你更看重改动成本与向后兼容，方案 B 是稳妥选择；两者也可以组合——A 的分栏 + 右栏顶部「本局 vs 个人最佳」对比卡是我认为的最优形态。

四、需要你拍板的 4 个问题

Q1 · 结算页方案　选 A（左右分栏）、B（底部固定栏），还是 A+B 组合（分栏 + 右栏加「本局 vs 最佳」对比卡）？
Q2 · 辅助面板默认态　「前 3 局默认展开，之后自动收起」这个策略你接受吗？还是希望一律默认收起、只保留展开按钮？
Q3 · 音效收敛范围　问题 ④ 你说「去掉除击球外所有声音」，我想再确认两点：
· 观众欢呼要保留吗？还是只保留「破纪录那一刻」的欢呼，其余掌声/零星加油全部去掉？
· 扣分反馈目前有下行音（bad），它是「失败提示音」而非「击球声」——一起去掉，还是保留作为必要反馈？
我倾向：只保留击球声 + 破纪录欢呼，扣分只靠画面与文案表达，最干净。
Q4 · 全屏与横屏锁定　全屏在 iOS Safari 上只能「网页全屏」（100dvh + 隐藏地址栏），真正的 requestFullscreen 与 orientation.lock 均不可用。你接受「安卓上真全屏 + 方向锁定，iOS 上网页全屏 + 现有横屏引导层」这个差异化降级吗？
