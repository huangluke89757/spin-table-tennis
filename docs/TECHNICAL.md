# 旋转乒乓 · 第一视角 3D

PC 端第一视角乒乓球反应小游戏。核心循环：**判断旋转 → 调整拍面 → 拖动击球 → 看失败原因**。

线上地址：**https://spin-pingpong.app.workbuddy.host/**（海报上的二维码就指向它）

零依赖运行：Three.js 已内置在 `vendor/`，不联网、不装包。

## 运行

双击 `index.html` 即可（推荐 Chrome / Edge / Firefox，需 WebGL）。
首次点击「开始对局」时会初始化音频（浏览器要求用户手势后才能出声）。

## 品牌

- 名称：**旋转乒乓**（英文 Spin Table Tennis）。
- Logo：一颗白球 + 上下两道旋转弧 + 箭头，见 `poster.js` 的 `logoSvg()` / `drawLogo()`。
  界面品牌行、开始页、结束页三处共用同一形状（HTML 里只写 `<span data-logo="26">` 占位，
  由 `injectLogos()` 统一注入；三处尺寸分别为 26 / 62 / 34），避免三份 logo 各画各的。
- **品牌行位置**：屏幕**左上角**，就在「连续回球」计数**上方** —— logo + 应用名，
  下方一条细分隔线与读数组分开。**左下角的半透明水印已移除**：
  它压在拍面栏上，既挡操作信息又和球台边缘抢视线，且"角落水印"本身是廉价感来源。
- 球拍运动痕迹：挥拍路径上留 16 片薄圆片残影（加法混合，不透明度上限 **0.15**，0.28s 淡出）。
  设计约束是「有，但不明显」——痕迹只做气流感，不能抢戏、不能遮挡来球。

## 控制

| 输入 | 作用 |
|---|---|
| 按住鼠标拖动 → 松手 | 松手即出拍。拖动**方向**定回球线路（左/中/右），拖动**速度**定力量 |
| 松手时机 | 球外光环缩到最小那一刻＝最佳击球点；越早弧线越高（出底线），越晚越容易下网 |
| 滚轮 / A · D | 调整拍面角度：接**上旋压拍**、搓**下旋亮拍**、侧旋与直球用**中立**拍面 |
| Shift | 正手 / 反手（球拍从左侧 / 右侧入画，动作演出不同） |
| Esc · P | 暂停（来球飞行与计时一起挂起） |
| H / M / R | 辅助提示 / 静音 / 重开 |
| Tab | 收起 / 展开辅助面板（拍面栏 + 操作说明 + 音效配置）。结束页也有一枚同功能开关 |

## 移动端（纯手势）

目标是「平板横屏可以纯手势完整游玩，桌面零回归」。四条设计决定值得记下来。

### ① 输入统一到 Pointer Events，但不做「鼠标事件顺手也认」

`mousedown/move/up` 全部换成 `pointerdown/move/up`。为什么不两套都留着：
在二合一设备（触屏笔记本）上，一次触摸会**同时**派出 pointer 与合成 mouse 事件，
两套监听都挂上就会一次挥拍触发两次 `doHit` —— 判定直接翻倍。

**代价（重要）**：`_smoke.js` 的测试桩原来派发 `mousedown`，改 pointer 后**静默全废** ——
自动玩家 6 局回球全部变成 0 拍、4 项球拍断言假红，且**没有任何报错**（监听器根本不响）。
所以桩必须同步改成派发 pointer 事件（见 `_smoke.js` 的 `PTR/fireDown/fireMove/fireUp/swing` 助手）。
同一轮改动把桩的「桩调用种类」从 67 拉回 69，正好是加入的两个 pointer 事件 —— 这个数字现在是
「桩与游戏输入契约是否对齐」的哨兵。

### ② 量纲按键型分两套：鼠标走绝对像素，触摸走视口比例

原版 `doHit` 的 `dx/140`、`len/190`、`speed/1100` 是绝对 CSS 像素常量。手机上屏宽只有桌面的
9.7%，照搬会让「手机击球精度需求 ≈ 桌面 3.7 倍」，手指根本点不准。

但**不能直接全局归一化**：桌面玩家是照着这套绝对像素练出手感的，改成按视口比例后，
同一台机器换个窗口大小手感就漂 —— 而「判定可信」正是这个项目的核心价值。

所以 `measureDrag()` 里按键型分叉（判据是 **`pointerType`，不是 `isCoarse()`**，
因为二合一设备上鼠标与手指要各按各的算）：

| 量 | 鼠标 | 触摸 |
|---|---|---|
| 最小挥拍幅度 | 10 px | `0.055 × vmin` |
| lenN 满值 | 190 px | `0.200 × vmin` |
| speedN 满值 | 1100 px/s | `0.850 × vmin` |
| aim 满幅 | 140 px | `0.260 × 视口宽` |

触摸系数刻意比「等比例换算」更宽松：手指落点精度 ≈1cm，远低于鼠标。
其余系数集中放在 `TOUCHSCALE`，方便真机调手感。

### ③ 双区手势：左 45% 调拍面 / 右 55% 击球

与原有的「左手键盘 / 右手鼠标」分工同构，玩家不需要重新建立直觉。左区只在**辅助关**时手动生效：

- 辅助关（挑战模式）→ 左区纵向拖拽手动调拍面
- 辅助开（练习模式）→ 拍面由每帧自动跟随 `correctTiltFor(G.spin)` 接管，左区手动**刻意忽略**

忽略是故意的：不忽略的话玩家的手会与自动角度互相打架。回归对这两态分别做了断言
（这条一开始把测试写错过一次，见 ⑤）。

### ④ 竖屏不是「体验差」，是几何上不成立

第一视角相机垂直 FOV 固定 40°（`CAM = PerspectiveCamera(40, aspect, 0.05, 60)`），
水平视野随 aspect 变化：

| 方向 | aspect | 水平 FOV | 击球带（z=HIT_Z）可见半宽 | 球台半宽 | 结论 |
|---|---|---|---|---|---|
| 平板横屏 844×390 | 2.16 | **76.5°** | **1.118 m** | 0.7625 m | 球台完整入画 |
| 手机竖屏 390×844 | 0.462 | **19.1°** | **0.239 m** | 0.7625 m | 球台被裁掉 2/3 |

竖屏时球还没飞到能被看见的位置就已经出画。所以 P2 的「请横屏」引导层是**几何结论**，
不是产品口味：`isSupported()` = 桌面(fine pointer) 或（coarse 且 ≥768px 且横屏）。
回归里这条从源码解析机位常量重算，与设计报告的数字交叉验证一致（19.1° / 0.239m）。

### ⑤ 触摸为什么必须四层 `touch-action:none`

只给 `canvas` 设是不够的。实测（报告 E2）：**触摸点落在 HUD 元素上时**，浏览器照样把序列
掐成 `pointercancel`。所以 `html` / `body` / `#hud` / `canvas` 四层都要盖，
外加 `overscroll-behavior:none` 防下拉刷新吃掉手势；`.rotate-hint` 与各交互控件（`.tbtn`、
`.mini`、range、模式卡）也各自设上。

`_touch_browser.js` 用 CDP 注入真实触摸序列，断言「全程零 `pointercancel`」——
这是真浏览器才验得了的，Node 桩里只能验「属性设了」。

### ⑥ 引导层必须完全不透明

`rgba(8,11,17,0.97)` 有个隐蔽问题：7% 的透光会让**开始页的模式卡片与按键表露出轮廓**，
在竖屏手机上看起来像「还能点」。引导层的职责是明确阻断，不是覆盖得差不多。
改成不透明径向渐变后视觉上才真的「这道门关上了」。

同理，`pointer-events:auto` 只是让触摸打不到下层，**视觉误导**得靠背景不透明度解决——
两者是两件事，缺一个都会让玩家去戳底下的按钮。

### 迁移陷阱记录

- **测试桩不同步 = 静默全废**：改输入层必须同步改桩，否则断言假红且无报错（见 ①）。
- **测试自己写错比代码错更常见**：本轮 3 项 FAIL 全出在测试侧 ——
  `togglePause` 有 `if (!G.running) return` 守卫（没进局就是空操作）、
  左区手动在辅助开时被刻意忽略（设计如此）、`CAM` 是 Proxy 桩读不到真 `fov` 值。
  修完 53/53。**断言失败先怀疑断言**。
- **探针脚本按用途分家**：`_touch.js`（逻辑契约，快，无浏览器依赖）、
  `_touch_browser.js`（浏览器真实行为，慢，需 Chromium）、
  `_live_touch.js`（线上产物复验，需 `--live`）三者分开，别混成一关。
  早期 5 个探索型探针已归档到 `_tools/probe-legacy/`。
- **线上复验必须验「内容」而不是「URL」**：CDN 完全可能出现新 URL 配旧内容。
  `_live_touch.js` 直接在线上页面调 `measureDrag`，比对触摸（`0.055×vmin`）与
  鼠标（原版 `10`）两套阈值 —— 这才能证明部署产物里的**代码逻辑**是新的。
  只查 `game.js?v=xxx` 有没有变是不够的。

## 辅助面板的显隐

屏幕两侧的辅助信息可以整体收起，让画面只剩球台与关键读数：

| 位置 | 内容 |
|---|---|
| 左下 | **拍面栏**（正/反手、拍面角度、辅助提示开关状态） |
| 右下 | **操作说明**（按键表） |
| 右下 | **配置栏**（音效开关 + 音量 + 显隐开关，配置类集中成组） |

**一个开关统管三块**：左下拍面栏与右下操作说明、配置栏一起收放，开关按钮住在配置栏里
（收起时只藏配置体，按钮留在原地）。

三条入口，共用同一个 `G.uiHidden` 状态：**Tab 键**、配置栏里的**收起/展开按钮**、
**结束页的「辅助面板 [显示/隐藏]」开关**。状态存 localStorage（`fpp_uihidden`），下次打开保持。

三个设计要点：

- **收起用 CSS 类而不是 JS 直接改 `style.display`。** JS 只切 `#hud` 上的 `ui-collapsed`，
  具体藏哪几块由 CSS 决定 —— 这样新增辅助面板只需往选择器里补一个 id，不用动 JS，
  也不会出现「JS 说藏了、CSS 还显示着」的两头维护。
- **开关按钮不能落在被收起的名单里。** `ui-collapsed` 规则只作用于
  `#hudFace` / `#hudKeys` / `#cfgBody` / `#cfgSep`，开关本身（`#btnUiToggle`）与
  它所在的配置面板（`#hudCfg`）留在原地 —— 否则一收起就再也点不开。回归对这条做了源码级断言。
- **配置类控件集中在一个面板**：音效开关、音量滑块、显隐开关同处 `#hudCfg`，
  用一条细分隔线分组，符合「配置项归到一起」的直觉。

**布局从结构上杜绝重叠**：右下两块用 `flex-direction:column` 竖向堆叠，
而不是各自写死 `bottom` 偏移（旧写法一处内容长高就会压到邻居）。
回归用真浏览器在 4 种窗口尺寸下量 `getBoundingClientRect` 两两求交，并要求交面积为 0。

## 玩法规则

- 一球失败即本局结束，成绩＝连续回球数，最佳纪录存 localStorage。
- **来球池**：明显旋转球（上旋/下旋/左/右侧旋）合计 **25%**，其余 75% 是慢速好接球
  （直线快球 45%、轻上旋 15%、轻下旋 15%）。轻上/下旋的 `|ωx|` 恒 < 60，
  无论打到第几档都是「拍面中立就能接」的新手友好球。
- **球速**：到位时间基准 0.74s（原 0.46s），**整体放慢约 40%**；每升一档减 0.03s，下限 0.50s。
  各球型另有快慢系数 —— 直线快球 ×0.88（最快）、轻上/下旋 ×1.06（最慢）。
- 每 4 拍升一档难度（球速＋、旋转＋），第 8 档封顶不再提升。
- **落点得分**：回球落点离黄圈理想落点越近越值钱（<0.13m 判「落点精准」，
  <0.065m 判「神来一板」），基础分 = 当前难度档，连续精准有滚雪球奖励 ——
  所以「稳」比「猛」更值钱，不会越打越急着加力。
- 辅助提示默认开启：来球类型、球上旋转箭头、预测落点圈、击球点标记；按 H 关闭后只能靠弧线判断。
- 失败时给出**具体原因**（吃旋转 / 时机早或晚 / 拍面太压或太亮 / 出界下网 / 出边线），并在球真实落点处打红叉。
- 失败后**静置 1.25s** 才弹结算界面，让玩家看清失败原因、落点标注与偏差读数
  （原为 2.5s，实测等待偏长，已减半；时长常量见 `game.js` 的 `SETTLE_WAIT`）。

## 音效

全部由 Web Audio 实时合成，无音频文件：

- **击拍**：带通噪声瞬态 + 三角波共振（音高随力量上升），叠一层方波泛音
- **落台**：更低的带通 + 更快衰减，力度取落台前的入射垂直速度
- **落地 / 挂网**：低通噪声钝响
- **完美击球**：上行三度短音；**升档**：三音上行 + 欢呼；**失误**：下行滑音 + 钝响
- **零星喝彩**（`sfxYell`）：单声短呼喝，发球前与回球成功时各有约 30%/20% 概率冒出
- **音量与静音**存 localStorage，配置栏与暂停面板两处同步

### 观众席（`sfxCrowd`）—— 共振峰合成

**曾经的问题**：用户反馈欢呼声是「轰轰轰」。根因有两层：

1. **球馆底噪**是 400Hz 低通噪声、**持续 loop 播放**，低频轰鸣从头到尾压着画面；
2. **欢呼的"人声"层**用 480~980Hz 窄带噪声（Q=5~9）冒充人声 ——
   那一段是"嗡"的频段，不是人声基频（人声基频在 100~300Hz），所以听起来只有一团低频轰响。

**现在的做法** —— 按人声的真实声学原理合成（声带基频 + 共振峰）：

```
每条嗓子 = 锯齿波（基频 110~280Hz，语调上扬再回落 + 5~8Hz 轻微颤音）
           → 三条并联带通（F1≈800 / F2≈1500 / F3≈2800Hz）
           → 包络（快速起音 → 拖长 → 衰减）
一群嗓子错峰起唱、音高互不相同 → 「哇——」的热烈欢呼
```

- 欢呼用 **18~30 条嗓子**，起唱时间用平方分布（开头瞬间涌上来一片 = 爆发式欢呼）
- 掌声 = 58~112 个极短高频 click（2.2~4.6kHz，另叠 900Hz 高通），
  起点抖动 ±12ms、6% 随机漏拍 → 自然的"不整齐"
- 人群"空气层" = 600Hz 高通 + 1.4~2.4kHz 带通的宽带噪声（只做垫底，不做低频轰鸣）
- 球馆底噪改为 **220Hz 高通 + 2.6kHz 低通**，增益降到 0.006（原 0.035）

**每次调用的嗓门数、鼓掌人次、时长、音高分布、底噪频率全部重新随机**，
所以不可能两次一样 —— 由回归断言直接校验（8 次调用必须产 8 组不同参数）。

### 声学验证（`_audio_spectrum.js` + `_audio_spectrum.py`）

代码结构对（"创建了振荡器"）**不等于听感对**。所以把 `game.js` 里
`rand` / `crowdVoice` / `sfxCrowd` / `audioInit` 的**真实源码**抽出来，
注入 `OfflineAudioContext` 渲染成 PCM，再做 FFT 逐层对比新旧：

| 指标 | 旧版 | 新版 |
|---|---|---|
| 底噪 <200Hz 能量占比（「轰」的根因） | **32.2%** | **1.0%**（降 97%） |
| 底噪谱质心 | 314 Hz（闷响） | 1993 Hz（空气感） |
| 人声层 80~400Hz 基频区能量 | 0.7%（几乎为空） | **10.4%** |
| 完整欢呼谱质心 | 940 Hz | 1746 Hz |
| 完整欢呼 >3.5kHz 空气感 | 1.4% | 13.2% |
| 完整欢呼 RMS 响度 | 0.0011 | 0.0041（更热烈，未因降噪变弱） |

对照图见 `_shots/cheer_spectrum_compare.png`（三联图：底噪 / 人声层 / 完整欢呼）。

> 为什么必须逐层隔离量：旧版掌声用了 1.15~2.6kHz 带通、数量又多，
> 会把**整体**质心拉到 900Hz 左右，于是"新旧质心差不多"——但听感天差地别。
> 必须把「掌声」与「人声」分开量，才能看出旧版人声层根本不含基频。
> 同理，"200-700Hz 能量更高"这类判据是错的：旧版带通中心正好落在该区间，
> 拿一个偏向旧版算法的区间去要求新版更高，是判据设计错误而非代码问题。

## 分享海报（方案A · 技术统计板）

破纪录时自动弹出（也可在结算页点「分享海报」），900×1360 逻辑尺寸、2× 导出 1800×2720。
全 Canvas 手绘（`poster.js`），不引外部截图库、不依赖网络。

**内容**：Logo + 游戏名 → 本局连续回球 / 得分 / 新纪录徽章 → 高光三连拍 → 三项指标卡 → 主视觉 → 二维码。

**高光三连拍**：只认「球击中**对手**球台」那一瞬间（`step()` 返回 `"table"` 且落点 `z < 0`），
按单拍得分取最高的 **3 张**，同分取后打出的一拍（越往后难度越高）。

**抓帧机制（离屏渲染，不闪主画面）**：抓帧要换三个戏剧化机位（见坑 #8），
旧实现在**主渲染器**上临时改机位 → `render()` → `toDataURL()` → 还原机位。
问题是这一次"补渲染"会真的画到**玩家的屏幕上** —— 于是击球成功的一瞬间，
画面会闪一下非第一视角的球桌。玩家把这一帧看得清清楚楚。

现在改为**独立离屏渲染器** `SHOT_REND` + 专用相机 `SHOT_CAM`（独立 canvas，640×400，
与机位标定画幅一致）。抓帧全程只碰 `SHOT_REND`，主画布**一个像素都不动**，
闪现从根上消失。连带好处：主渲染器不再需要 `preserveDrawingBuffer: true`
（那是"抓主画布"才需要的选项，它会常驻多一份帧缓冲），渲染开销也降了。

**三项指标**（用户选定「命中 + 精度 + 力量」）：

| 指标 | 口径 |
|---|---|
| 旋转球接发率 | 接住的旋转球 / 面对的旋转球。判据 `\|ωx\| ≥ 60 或 \|ωy\| ≥ 60`，与 `correctTiltFor` 同一阈值 |
| 落点精度 | 平均 `\|二次落点 − 理想落点\|`，单位 cm |
| 最快回球 | 本局最高出手速度 `max(5.0 + power×3.1)`，×3.6 换算 km/h |

**二维码**：矩阵**直接内联在 `poster.js`**（29×29 位 → base64 144 字符，`QR_N` / `QR_B64` 两个常量），
由 `drawQR()` 用 `fillRect` 同步绘制，不加载任何图片文件。
`_qr.py` 读 `game.js` 的 `GAME_URL` 重新编码并改写这两个常量；换线上地址只需改 `GAME_URL` 再重跑 `python _qr.py`。

> 为什么不用图片文件：早先用 `<img src="vendor/qr.png">`，踩了两个坑——
> ① `file://` 下算跨域，画进 canvas 污染画布，点「保存图片」抛 `SecurityError`；
> ② 图片是**异步**加载的，文件一旦漏传或加载慢于海报弹出，就静默降级成占位空框。
> 线上曾因漏传 `vendor/qr.js` 出现整块白框，而当时的弱断言（只查深色像素占比）照样通过。
> 改成内联同步绘制后，**海报画得出来，二维码就一定在**。

## 视觉风格

深色单一强调色体系，配色变量集中在 `index.html` 的 `:root`；`game.js` 的 `C` 对象是 3D 场景侧的同一套色值，两侧改动需同步。
海报沿用同一套色值（`poster.js` 的 `COL`），三处改动需同步。

## 球网建模（按 ITTF M2 器材标准）

旧版球网的问题是**颜色用反了**，而不是建模精度不够：

| | 旧版 | ITTF M2 要求 | 现版 |
|---|---|---|---|
| 网纱（mesh） | 白色网格 `rgba(230,238,246,.85)` + `opacity 0.55` | 亮度必须 **< 50%**（暗绿 / 暗蓝） | 深墨绿 `rgba(14,46,38,.72)` + 网线 `rgba(96,168,142,.85)` |
| 网顶带（tape） | 缺失 | 必须白/浅黄，且与网纱**明显区分** | 白色 `BoxGeometry`，带下压一条暗缝 |

白色网纱叠在白色桌线附近，**同色同亮度** → 糊成一片，这正是用户反馈的
「球网和球桌划线重叠、缺少立体感」。改完只有对比还不够，又补了三层立体信息：

1. **纵向明暗渐变**（`createLinearGradient`）：顶亮底暗，这一层就是「厚度感」的来源。
   没有它，网永远像一张贴在空中的贴纸。
2. **网顶带做成有体积的盒子**（非平面），受光后自然有别于网纱；带头下沿补一条 `tapeShade` 暗缝，
   模拟带子垂下来的投影。
3. **网柱**（左右两根 `BoxGeometry`）+ 柱脚 `foot` + **网根接地影**（两层，压出台面的前后关系）。

网宽用 `T.netHalfW * 2`（ITTF 标准 1.83m），网高 `T.netH`（15.25cm），不再单独存深度常量。

**海报同步**：海报的主视觉是**复用同一个 3D 场景**抓的帧（见「分享海报」一节的抓帧机制），
所以球网改色改形后海报自动同步，不需要在 `poster.js` 里再画一遍。

复核方法：`python _netcrop.py` 从 `_shots/09_poster_full.png` 里按 `poster.js` 的排版常量
（`sy=436 sh=196 sw=272 gap=10`，导出 2×）精确裁出高光三连拍并放大 3 倍。
**不要靠目测比例去裁** —— 我一开始按百分比裁，连裁两次都偏上一个身位，白费两轮。
三个机位下球网都清晰可辨：深绿网纱有网格纹理、白网带独立成带、网柱有体积、台面有接地影。

## 球拍几何（按真实横拍尺寸）

尺寸集中在 `game.js` 的 `RKT` 常量对象里，全部以米为单位、对着实物标：

| 部位 | 现版 | 真实横拍 | 说明 |
|---|---|---|---|
| 拍面直径 | **152mm** | 152mm | 拍面 152×155mm 的标准值 |
| 握柄长度 | **95mm** | 95mm | 柄长/拍面 = **0.625**（旧版 0.26，柄短得像玩具） |
| 拍面纵横比 | **1.02**（略高椭圆） | 1.02 | 见下方"椭圆失效"的坑 |
| 全长 | **257mm** | ≈255mm | 拍面 + 柄 + 柄底 |
| 前臂 | **130mm** | — | 旧版 260mm，粗 96mm，拖在画面外像根柱子 |

> **椭圆拍面曾经是"改了没生效"的假修复**：旧代码写 `blade.scale.y = 1.26`，
> 但拍面网格 `rotation.x = π/2`（躺平），局部 y 轴此时指向**厚度**方向 ——
> 于是这个缩放一直作用在厚度上，拍面从头到尾都是**正圆**。
> 改成 `blade.scale.z = OVAL` 才真正压成椭圆。**缩放要写在旋转之后的等效轴向上，别想当然。**

## 消息系统（优先级 + 保护期 + 排队）

夸奖提示曾经「一闪就没了」，根因是**单槽覆盖**：任何新消息直接覆写 `G.msg`。

现在 `showMsg(text, sub, color, dur, pri, hold)` 带两个新参数：

- `pri` 优先级：`3` = 失败类（最高，随时可打断）/ `2` = 大夸奖 / `1` = 常规
- `hold` 保护期（秒）：这段时间内**低优先级消息只能排队**，不能顶掉当前提示

主循环每帧推进 `msgT`（显示时长）与 `msgHold`（保护期），保护期走完才放行排队消息
（队列上限 4 条，防止攒一堆过期提示）。

| 提示 | 时长 | 优先级 | 保护期 |
|---|---|---|---|
| 好球 | **1.9s**（原 0.6s，延长 217%） | 1 | 1.5s |
| PERFECT | 2.1s | 2 | 1.7s |
| 落点精准 | 1.7s | 2 | 0.55s |

失败类消息 `pri=3` 可以直接打断任何提示 —— 失败信息必须立刻看到，不能排队。

## 结算中动画

击球失败到球局结束统计之间原本是**纯黑等待**，观感像卡住了。

现在 `fail` 末尾调 `showSettle()`，切 `#settle` 的 `on` 类，出一个**乒乓球主题**的过渡：

- 一颗球上下弹跳（`stBall` keyframes）+ 下方影子随高度呼吸（`stShadow`）—— 有乒乓球元素
- 「结算中」三个字 + 游标点循环（`stDot`）
- 一条进度条（`stBar`），把"还要等多久"明确告诉玩家

**时长只有一个真值来源**：`game.js` 的 `SETTLE_WAIT`（当前 **1.25s**，原 2.5s 减半）。
它同时驱动三处，改一处即可：

| 受控对象 | 怎么拿到这个值 |
|---|---|
| 结束页弹出时机 | `G.overAt = G.gt + SETTLE_WAIT` |
| 失败提示停留 + 保护期 | `showMsg(tag, …, SETTLE_WAIT, 3, SETTLE_WAIT)` |
| 进度条动画时长 | `showSettle()` 写入 CSS 变量 `--settle-wait`，CSS 里 `animation:stBar var(--settle-wait)` |

进度条**不再写死秒数**——否则改 `SETTLE_WAIT` 时进度条还走老时长，动画与结束页对不上。
`index.html` 的 `#settle` 保留了 `--settle-wait:1.25s` 作兜底，防止 JS 未执行时动画停住。
弹跳周期 0.62s ≈ 窗口的一半，1.25s 里弹两下：读得出「在动」，又不会晃得心烦。

细节：重播动画前先 `void el.offsetWidth` 强制 reflow，否则连续两局失败时
浏览器认为类名没变、动画不会重新开始。`gameOver` / `restart` 都调了 `hideSettle()`，
避免动画残留到下一局。

## 双模式（练习 / 挑战）

两个模式的差异**只有一处**：辅助提示。

|  | 练习模式 | 挑战模式 |
|---|---|---|
| 辅助提示 | 默认开（`H` 可关） | **强制关**（`H` 无效） |
| 成绩 | 不计入排行榜 | 计入历史前十与每档最佳 |
| 分享海报 | 不标「新纪录」 | 破纪录可标 |

**为什么不在难度 / 球速 / 来球池上也做区分**：一旦区分，两者就变成「两个游戏」——
榜单与失败统计失去可比性，玩家也无法把练习里积累的经验迁移到挑战模式。
双模式存在的意义是「给新手一条低门槛路径，但不降低高门槛路径的标准」，
这是避免**「为留住新手而降难度」这条转嫁负担陷阱**的机制设计（降难度会侵蚀
「旋转辨识」这个核心价值，产品会退化成又一个无脑乒乓）。

**为什么执着于「挑战模式不能开辅助」**：挑战模式的全部意义就是「无提示下的真实水平」。
留一个后门会让榜单立刻失去可比性 —— 那这套纪录系统就白做了。
`keydown` 的 `h` 分支直接拦掉并给一条提示说明原因，而不是静默失效
（静默失效会让玩家以为键盘坏了）。

`setMode(m)` 是唯一入口：它设置 `G.mode`、按模式决定 `G.assist`、持久化、刷新卡片高亮。
`loadPrefs()` 里读出的 `fpp_assist` 只代表**练习模式的偏好**，
所以 `boot()` 里必须 `loadPrefs()` → `setMode(loadMode())` 这个顺序 ——
反了的话挑战模式会带着辅助提示开局。

## 本地纪录系统

纯前端，无账号无服务器。数据契约（结构改动需同步 `_tools/_smoke.js` 的断言）：

```
fpp_mode     "practice" | "challenge"
fpp_records  {
               best:  { practice:N, challenge:N }   每模式最佳回球数
               score: { practice:N, challenge:N }   每模式最佳得分
               level: { "1":N ... "8":N }           每档最佳（仅挑战模式）
               history: [ {rally,score,level,mode,good,ts} ]  按 score 降序，最多 10 条
             }
fpp_best / fpp_best_score   旧版单值。首次启动迁移进 fpp_records 后不再写入，
                            但**保留不删** —— 万一玩家回退到旧版本，纪录还在。
```

三个设计要点：

- **历史榜只收挑战模式成绩**。练习模式开着辅助提示（且可随时开关），成绩没有可比性 ——
  这条规则是排行榜可信度的前提。竞品排行榜普遍失去玩家信任（Ping Pong Fury 的
  「装备碾压」、Virtual Table Tennis 的「外挂刷榜」）都源于同样的规则漏洞。
- **每档最佳只在挑战模式记**。混着算会让「某档最佳」失去意义。
- **所有读写都包 `try/catch`，`loadRecords()` 逐字段兜底**：隐私模式会直接禁掉
  `localStorage`，内容也可能被用户手改坏，任一情况都不该让游戏起不来。
  任一项类型不对就退回默认值，而不是让整套纪录瘫痪。

## 失败归因（5 个桶）

把一次失败收敛到玩家能理解的 5 类，并在结束页汇总成本局构成。

| 桶 | 触发情形 |
|---|---|
| 吃旋转 | 拍面偏差 + 强旋转；侧旋没做横向补偿 |
| 拍面偏差 | 拍面压太狠 / 太亮 / 角度不对 |
| 时机早或晚 | 击球太早或太晚 |
| 力量与落点 | 力量太大 / 太小、回球线路太偏 |
| 没打到球 | 完全漏球、挥拍幅度不足 |

**归类依据刻意用提示文案里的关键词，而不是重算一遍 `tiltErr` / `dt` 的阈值。**
原因：`reason()` 已经决定「告诉玩家什么原因」，如果这里再独立算一套阈值，
两者会出现「提示说吃旋转、统计记成拍面偏差」的自相矛盾 —— 玩家一旦发现数据
和自己刚看到的那句话对不上，整个归因功能的可信度就没了。用文案反推，
保证桶一定与那句话一致。

**计数用 `phase` 做闸门**：同一拍可能被多处判定命中（`doHit` 里多个 `fail` 分支、
外加主循环的漏球兜底），重复计数会让「失败构成」失真。`fail()` 自身会把 `phase`
置为 `"miss"`，天然幂等。

游戏本体只有根目录三个文件（`index.html` / `game.js` / `poster.js`），

## 代码结构

`game.js`：

| 段 | 内容 |
|---|---|
| 1 | 常量、回球公式系数 `K`、球型池 `SPIN_POOL`、场景配色 `C` |
| 2 | 物理内核（纯计算，无渲染依赖）：重力 + 空气阻力 + 马格努斯力 + 台面摩擦 + 旋转衰减，`accel / step / shoot / solveServe` |
| 3 | Three.js 场景：球台、网、球（带贴图可看自转）、旋转箭头、残影、**球拍运动痕迹**、预测落点、失败标注、击球点标记、对手、玩家球拍（正/反手两支） |
| 4–6 | 游戏状态、来球与判定、输入 |
| 7 | 音效合成 |
| 8–11 | 主循环、渲染、**抓帧与残影渲染**、HUD、启动、**海报数据与弹出** |

`poster.js`：Logo 生成（Canvas + SVG 双版本）、变宽笔迹与拍影、海报排版、导出。

### 物理与判定要点

- 弹道是**真 3D**：马格努斯力 `F = MAG_K · (ω × v)`，上旋下坠快、下旋飘、侧旋空中弯、落台侧跳，全部由同一套公式自然涌现。
- 发球用 `solveServe` 网格搜索：过网 → 落对手半台 → 落玩家半台 → 击球点在可打高度与台面横向范围内，逐级放宽保证一定能发出合法球。
- 回球公式系数 `K` 由离线全维度搜索标定（球型 × 击球高度 × 力量 × 击球横向位置），**改 K 必须重跑回归**。

    竖屏引导层铺满全屏且**屏幕中心命中它就是它**（对局真的不可达）、桌面零回归。
    与第 5 关的分工：那关验逻辑与契约（快、可无浏览器跑），这关验浏览器真实行为（慢、需 Chromium）。
13. `_live_verify.js` — **线上端到端验证**（需 `node _run_all.js --live`）：打开线上地址，
   ① 回读海报二维码 841 位；② 点开关确认辅助面板可切且拍面栏同步收放；
   ③ **线上特征探针（12 项）** —— 尤其"离屏抓帧"这条：给 `REND.render` 装计数钩子，
   在同步块内跑一次 `captureShot`，断言**主渲染器调用次数为 0**（这正是闪现 bug 的根因，
   用计数直接证明，而不是查 `SHOT_REND` 存不存在）；另按**几何参数**在场景里认领球网三层结构
   （不靠对象名）、按 `RKT` 换算拍面/柄的毫米数、查品牌行与结算动画 DOM。
   其中两条专门盯 **CSS 改动有没有上线**：`--settle-wait` 是否为 `1.25s`、
   进度条 `animation-duration` 是否同为 `1.25s`（读计算样式，不查 DOM ——
   新旧两版 DOM 都在，只有样式能区分版本）。
   本地 `file://` 全绿**不能**证明线上是好的（曾因漏传 `vendor/qr.js` 线上白框，
   也出现过"新 index.html + 旧 game.js"的 CDN 错配）。
14. `_live_touch.js` — **线上移动端手势复验（27 项）**：打开线上地址，四个场景
   （A 静态契约 / B 平板横屏 / C 手机竖屏 / D 桌面零回归）。
   与第 13 关的分工：那关验的是历史功能（离屏抓帧 / 球网 / 双模式），**一条都没覆盖移动端改造**；
   移动端这次横跨 `index.html`（CSS / DOM / viewport meta）与 `game.js`（量纲 / 门控 / 手势），
   正是 CDN 新旧错配的高危区，必须单独复验。
   **最硬的一条证据是「内容」而不是「URL」**：直接在线上页面里调 `measureDrag`，
   比对触摸（`0.055 × vmin`）与鼠标（原版 `10px`）两套阈值 —— 版本戳只能证明
   `game.js?v=xxx` 变了，证明不了里面换没换；这一条能。
   其余：四层 `touch-action` 计算样式直读线上、真实触摸回球得分（8/8）、
   竖屏引导层铺满且屏幕中心命中它、桌面鼠标量纲仍是原版（手感零回归的线上证据）。

> 第 3 关为什么必须存在：性能优化最容易悄悄改坏物理。`accel()` 返回数组改成写复用对象、
> `Math.hypot` 换成手写 `sqrt`，看起来只是"写法问题"，但浮点运算顺序变了。
> 实测 4320 条弹道**逐位零差异**才敢合并 —— 而且这个对比必须在**独立进程**里跑：
> 同一 `eval` 作用域下第二次定义会覆盖第一次，两边其实是同一份代码，永远"0 差异"（假绿）。

> 第 7 关为什么必须存在：重叠是「盒子在屏幕上的位置」问题。Node 桩里 `getBoundingClientRect`
> 是写死的常量，`classList` 也是空实现 —— 桩测能证明"类加上了"，但证明不了"看起来没叠"。
> 所以这一关只能在真浏览器里量。另外要**先隐藏所有浮层再量**：开始页 `z-index` 更高，
> 本来就该盖住 HUD，不先关掉会量到浮层而不是真实布局。

> 第 8/9 关为什么必须存在：代码结构对（"创建了振荡器"）**不等于听感对**。
> 参数写错（共振峰增益太小、基频太低）照样是轰鸣，桩测照样全绿。
> 只有把真实代码渲染成 PCM 做 FFT，才能客观证明"轰轰轰"真的被修掉了。
> 渲染脚本的底噪参数**从 `audioInit` 源码解析**而不是硬编码 —— 曾经硬编码 0.012
> 而 `game.js` 已改成 0.006，量出来的就不是线上真实听感。

> 第 6 关为什么必须存在：第 5 关是拿 `poster.js` 自己的矩阵去比对画布，**两边同源**——
> `QR_B64` 常量本身写错的话，会一起错、测试照样全绿。必须有独立信源才算验过。
> 排查二维码时也用它：`python _qr_verify.py` 一条命令就能判断"是常量错了还是绘制错了"。

`_shot_calib.js` 是抓帧机位标定脚本（扫方位角/仰角/距离，求「对方半台完整入画」的距离），
改机位角度时用它重标，别手算坐标。
`_netcrop.py` 按 `poster.js` 的排版常量从成品海报里裁出高光三连拍并放大，用于**肉眼复核**
海报里的球网/球台（自动断言只能证明"抓到的是真画面"，证明不了"里面的球网好不好看"）。
`_settle_shot.js` 抓「结算中」过渡动画的三帧（球在低处 / 高处 / 进度条推进），
用于复核这一层在任何背景下是否可读 —— 布局类问题同样只能靠眼睛看。
`_audio_plot.py` 把声学验证结果画成三联对比图（`_shots/cheer_spectrum_compare.png`），
供人工复核，不是回归的一部分。

`_smoke.js` 的 43 项缺陷专项覆盖率这几类回归风险：来球分布与球速、球拍入画（含失败情形）、
握柄几何、结算延迟、观众声随机性与**人声合成方式**、辅助面板显隐三入口与**拍面栏同收放**、
**离屏抓帧（不闪主画面）**、**球网 ITTF 规格三层结构**、**左上品牌行位置与左下角水印移除**、
**好球提示时长与保护期排队**、**结算中过渡动画**。
**改这几块必须跑 `_run_all.js`。**

> 发球求解器用 `Math.random()` 选起始横位，侧旋这类苛刻组合约 1/40 概率在 5 级放宽内仍解不出，
> 此时 `serve()` 退化为直球。测试链路已覆盖同一条兜底路径（`solveRetry` 返回 `degraded` 标记），
> 所以 40 次连跑不会再随机报错 —— 但**如果你看到「走直球兜底」频繁出现，说明旋转强度调过头了**。

`_calib3.js` 是参数标定脚本（离线搜索 `K`），满分 732/732，不是回归的一部分，改动回球公式时用它重标。

## 踩过的坑（改这几处前先读）

1. **球「变形」不是几何问题，是残影问题。**
   残影球半径是 `BR * 0.62` 再乘 `0.30~1.00`，最大时和真球一样大，14 个叠在一起，
   远距离只有几个像素时就糊成一团椭圆。现在残影压到 `BR*0.5` × `≤1.0`、不透明度 ≤0.15、加性混合。
   球本体也拆成「内层贴图球（自转）+ 外层正球光晕」，光晕在屏幕投影不足 3.5px 时自动撑开，
   保证远台来球也是一个能看清的圆点。

2. **球拍「出现太慢 / 不出现」有三层原因，缺一不可。**
   - `MISS_Z` 原为 1.85。相机在 z=2.72，球飞到 1.9~2.4 正对镜头，放慢球速后会在那里停 0.25~0.45s；
     游戏抢先判「漏球」，于是 `mouseup` 里 `G.phase === "incoming"` 的守卫直接跳过 `doHit`。
     球拍永远没机会出现 → 放到 **2.55**。
   - 原实现只在「打中」分支里启动球拍演出，所以「漏球 / 没打实」两种失败情形下球拍完全不出画。
     现在统一走 `showSwing()`，只要玩家挥了拍就一定演出。
   - 入画点原在 `(side*0.34, 0.95, 1.66)`，投影到 NDC 的 y ≈ **-0.83**（屏幕最底边），
     只占屏高约 5%，贴边贴底到没人注意到。现在抬到中下区（NDC y ≈ -0.30）。
     注：曾整体放大 1.35×，结果刀身在击球点糊满大半个屏幕像「玩具拍怼脸」，已回调 1.0×，
     靠抬高入画点而不是放大来解决。`_shot.js` 会直接量投影与屏幕占比，**上下界都卡**。

3. **握柄「太长」其实是比例失真（本轮已按真实尺寸整体重做）。**
   早期的修法是缩总下探（0.170m → 0.140m），治标；真正的观感问题是柄长配刀身的**比例**。
   当时代价改到柄长 0.050m / 刀身 0.192m（比例 0.26），虽然"像球拍了"但**离真实横拍很远**
   （真实柄长/拍面 ≈ 0.625）。本轮按实物标尺重做：拍面 **152mm**、柄 **95mm**、
   全长 **257mm**、前臂 **130mm**，尺寸集中在 `RKT` 常量里，回归按真实规格卡数值区间。
   **教训：观感 bug 的第一版修法常常只是"看起来不那么怪"，而不是"对了"。**
   有条件时应该去找真实规格作为标尺，否则会在一个错误的比例上反复微调。

4. **`_smoke.js` 里的正则必须写成 `RegExp("...")`。**
   测试代码是塞进模板字符串再 `vm.runInNewContext` 的，直接写 `/foo\(/` 字面量，
   反斜杠会被模板字符串吃掉一层，运行时抛 `Unterminated group`。用 `RegExp("foo\\\\(")`。

5. **断言「球拍可见」不能只查 `.visible`。** 球拍真的渲染了、`visible === true`、
   但落在屏幕最底边没人看得见。必须量**投影坐标 + 屏幕像素占比**才算验证过。

6. **`toDataURL` 抓到全黑 → 忘了 `preserveDrawingBuffer`。**
   WebGL 默认在 `render()` 之后立刻清空绘图缓冲，回调里再 `toDataURL` 只能拿到黑图。
   早期解法是给主渲染器加 `preserveDrawingBuffer: true`。
   **但本轮改用离屏渲染器抓帧后（见坑 #18），这个选项已从主渲染器移除** ——
   改成加在离屏渲染器上，且主画布不再被读取。`_poster_shot.js` 仍会把抓到的图解回像素、
   算平均亮度来卡"抓到的是真画面而非全黑"（全黑会被判失败）。

7. **二维码不能依赖任何异步资源——这是「海报出现白框」的根源，踩过两次。**
   第一次：`<img src="vendor/qr.png">` 在 `file://` 下算跨域，画进 canvas 后画布被污染，
   玩家点「保存图片」时 `toBlob` 直接抛 `SecurityError`。改用 data URI 内联版 `vendor/qr.js` 绕过了跨域。
   第二次（更隐蔽）：**但 `vendor/qr.js` 仍是一个独立文件、仍要异步加载**。
   线上部署时漏传了它，`window.QR_DATA_URI` 是 `undefined` → 回退 `vendor/qr.png`（404）
   → `setQR` 从未被调用 → 海报左下角画出**白底 + "二维码"三个字的占位空框**。
   而当时的断言是「二维码区域深色像素占比 > 0.15」，**占位框的边框也能凑够**，测试全绿但线上是坏的。
   现在二维码矩阵**直接内联进 `poster.js`**（`QR_N` / `QR_B64`），`drawQR()` 用 `fillRect` 同步绘制，
   零文件依赖、零异步、零跨域。断言也换成**逐模块回读比对**（841 位全等）+ 定位图案校验，
   并新增第 6 关用 python `qrcode` 独立重编码做交叉验证。
   **教训：验证「某个东西存在」时，别用「像它存在」的弱指标（像素占比、`visible` 标志）；
  要能回答"内容对不对"，并且必须有一个独立于被验证对象的信源。**

8. **固定机位的三张截图会长得一模一样。**
   游戏是第一视角固定机位，直接截三帧贴到海报上就是三张同样的照片。
   现在抓帧时**临时切一个戏剧化机位补渲染一帧**（低机位斜视 / 越肩 / 俯拍三个角度轮流），
   取完图立刻还原机位。机位用「方位角/仰角/距离」参数化并**瞄准对方半台中心**——
   瞄准球台中心会让镜头后退、落点缩成小点，还会把近端推到镜头正下方挤出画面。
   距离用 `_shot_calib.js` 扫出来，别手写坐标。

10. **别只数音源个数来断言「每次观众声都不一样」。**
    `sfxCrowd` 的音源个数只有约 55 种取值，8 次抽样必然撞生日碰撞（实测约 1/3 概率假失败）。
    现在比较的是**参数指纹**（人数 + 时长 + 底噪频率 + 底噪强度，全是连续随机量）。

11. **「不重叠」这类布局要求，Node 桩测不出来，必须真浏览器量。**
    右下两块原本各自写死 `bottom: 18px / 66px` —— 手写偏移量，任何一处内容长高一点就压到邻居。
    桩测里 `getBoundingClientRect` 返回的是写死的常量、`classList` 是空实现，
    所以「类加上了」能测，「看起来叠没叠」测不了。
    现在改成 `flex-direction:column` 竖向堆叠（结构上就不可能重叠），
    并新增第 7 关在真浏览器里 **4 种尺寸**下两两求交，要求交面积恒为 0。
    另外那条断言最初误报，是因为**没先关掉开始页浮层**（`z-index` 更高、本来就该盖住 HUD）——
    量 HUD 布局前必须先进入对局态。
    还有一处误报：**父子元素必然相交**。开关按钮住在配置面板 `#hudCfg` 里（设计上要求的"配置类归到一起"），
    拿它去和父面板求交必然得 2104px²。求交只能针对**并列**的内容块，开关单独做「是否被遮挡」检查。

12. **收起/展开的开关按钮，绝不能放在被收起的名单里。**
    规则一旦作用于整个容器，开关自己也被藏了 —— 收起就再也点不开，只能刷新页面。
    规则必须精确到只藏内容块（`#hudFace` / `#hudKeys` / `#cfgBody` / `#cfgSep`），
    开关与它所在的配置面板留在外面。回归里对这条做了源码级断言（解析 CSS 选择器），
    外加 `elementFromPoint` 命中测试确认按钮没被别的元素盖住。

13. **`classList` 桩不能是空实现。**
    冒烟测试原来的 `classList` 是 `{ add(){}, remove(){}, toggle(){}, contains:()=>false }` ——
    面板显隐全靠这个类，空实现会让「收起生效了吗」这类断言**永远假绿**。
    改成用 `Set` 真实记账后，才能测出状态流转。

14. **在沙箱模板字符串里写正则，反斜杠会被吃掉（第 4 条的另一面）。**
    断言 CSS 选择器和底噪高通滤波器时，我把正则写进了 `testCode` 模板串里，
    `\s` 被模板先吃成 `s`，正则静默失效、断言永远假绿（还打印出 `(未找到)` 这种假通过）。
    现在**源码文本断言一律在 Node 侧做**（`HTML` / `code` 在 Node 侧是完好的），
    只有运行时状态才在沙箱里量。

15. **「听起来是轰轰轰」不能用代码结构断言来证明修好了。**
    断言「创建了锯齿波振荡器 / 有 2.4kHz 共振峰」只能说明**代码走了那条分支**，
    参数错（共振峰增益太小、基频太低、底噪增益太大）照样是轰鸣。
    真正的判据是把真实代码渲染成 PCM 做 FFT。
    而且**必须逐层隔离量**：旧版掌声用 1.15~2.6kHz 带通、数量又多，会把整体质心拉到 900Hz，
    于是"新旧整体质心差不多"；把掌声与人声分开量，才看出旧版人声层根本不含基频（80~400Hz 仅 0.7%）。
    最后定位到的真凶其实有两层 —— **持续 loop 的球馆底噪**（<200Hz 占 32.2%）比欢呼本身更"轰"。

16. **物理热路径的"写法优化"会改变浮点结果，必须逐位验证后才能合并。**
    `solveServe` 是网格搜索：一次发球要跑约 480 条弹道 × 最多 700 步积分。
    两个热点都在 `step()` 里：
    - `accel()` 每步 `return [ax, ay, az]` → 每次调用一次堆分配，实测比写进**复用对象**慢 **4.8 倍**
    - `Math.hypot(a, b, c)` → 比手写 `Math.sqrt(a*a+b*b+c*c)` 慢 **2.6 倍**（hypot 要做溢出保护）

    改完单次发球从 **~50ms 降到 ~25ms**（提速 2 倍），`_phys_test.js` 的性能项从
    "44ms 失败"回到 "25ms 通过"。
    但**这两处改动都会改变浮点运算的舍入**，所以不能只看测试通过就合并 ——
    `_phys_perf.js --compare` 跑 4320 条弹道逐位比对，确认**零差异**才算安全。
    另外对比脚本必须在**独立进程**里跑两个版本：同一 `eval` 作用域下第二次定义会覆盖第一次，
    两边其实是同一份代码，会得到"0 差异"的**假绿**（我第一次就踩了这个）。

17. **性能断言不要用「多次平均 + Date.now()」，那是不稳定测试。**
    原来的写法是 30 次循环取平均、阈值 40ms。问题有三：
    ① 首次调用要过 JIT 解释器，冷启动被算进平均；
    ② 平均值受系统调度、GC、其它进程污染 —— 我并行跑回归时就出现过一次假失败；
    ③ `Date.now()` 只有 1ms 分辨率，对 20~30ms 的量级太粗。
    而更根本的问题是**阈值卡在运行时差异区间**：同一份代码 Node 25 是 31~34ms、Node 22 是 39~43ms，
    40ms 的阈值让同一份代码时绿时红。
    现在改成：**预热 3 批 → 跑 6 批各 10 次 → 取最小值**，阈值 35ms
    （优化后实测 Node 22 ≈ 25ms、Node 25 ≈ 20ms，留 30% 余量；若回归到优化前的 ~45ms 必然触发）。
    取最小值而非平均，是因为最小值反映"这段代码能跑多快"（性能容量），
    平均值只反映"当时机器有多忙"。

18. **抓帧不要在主渲染器上做 —— 玩家会看见那一次"补渲染"。**
    旧实现抓帧要换机位重渲染一帧，改的是**主渲染器**，所以它会真的画到屏幕上，
    表现为击球成功瞬间闪一下非第一视角的球桌。这不是"抓帧太慢"或"时机不对"，
    而是**用错了渲染目标**。
    现在用独立离屏渲染器 `SHOT_REND` + 专用相机 `SHOT_CAM`（独立 canvas），
    抓帧全程不碰主画布。回归做了两条源码级硬断言：
    ① 主渲染器构造里**不再有** `preserveDrawingBuffer`；② `captureShot` 函数体内
    **无任何主渲染器调用**（正则加了词边界 `(?<![A-Z_])`，否则 `REND\.render` 会误匹配
    `SHOT_REND.render` 子串，把离屏实现判成"还在用主渲染器"）。

19. **`scale` 作用在哪根轴上，取决于当时的 `rotation`。**
    拍面网格 `rotation.x = π/2` 躺平后，局部 y 轴已指向厚度方向。旧代码写
    `blade.scale.y = 1.26` 想压椭圆，实际一直在改**厚度**，拍面始终是正圆。
    改 `scale.z` 才生效。**别按"世界坐标直觉"写局部缩放。**

20. **颜色"重叠糊成一片"要先查亮度对比，不是先加描边。**
    球网与桌线糊在一起，第一反应是给网加高光/描边。但根因是网纱用了**白色**
    （`rgba(230,238,246,.85)`），在白色桌线附近同色同亮度，加什么描边都是往"更白"的方向叠。
    查 ITTF M2 规格后发现正确解法是**把网纱做暗**（<50% 亮度），网带做白 ——
    对比是靠**拉开明度差**得到的，不是靠叠细节。

21. **测试断言"时长/参数"要直接读源码字面量，别在运行时抓。**
    验证"好球提示延长到 1.9s"时，最初在运行时读 `G.msgT`，但读到的可能是接替它的
    下一条消息（「落点精准」），得到假失败。改成解析 `succeed` 里
    `showMsg("好球", ...)` 的**字面参数**，才测的是"代码写的就是 1.9s"。

22. **版本戳只覆盖 `poster.js` / `game.js` / `three.min.js` —— 只改 HTML/CSS 时它失效。**
    本轮给结算层补底衬（纯 `index.html` 的 CSS 改动），跑 `_stamp.py` 输出
    "版本戳已是 v66390e62，无变化" —— 因为三个脚本的联合哈希没动。
    而 `index.html` 本身**没有版本戳**，CDN 完全可以继续返回旧 HTML：
    脚本全是新的、样式却是旧的。这是继"`/` 与 `/index.html` 是两个缓存条目"之后，
    CDN 缓存问题的第三种形态。
    **解法**：① 线上探针直接**读计算样式**（`getComputedStyle(#settle).backgroundColor`
    是否为半透明）而不是查 DOM 元素是否存在 —— 元素两版都有，样式才有区别；
    ② 探针要先把 `display:none` 的元素点亮（`classList.add("on")`）才读得到计算样式。
    **改 HTML/CSS 后必须重新部署并跑 `--live`**，不能只看本地截图。
    实测：本平台重部署后会刷新 `index.html` 的缓存（本轮重部署后线上探针**第 1 次即通过**），
    所以这条断言是**防线**而非日常故障 —— 一旦哪天它红了，说明缓存没刷干净，
    而不是代码坏了。这比"重部署后肉眼看一眼"可靠。

## 踩过的坑（本轮新增）

23. **`#hud` 的 `z-index` 会困住子元素。**
    给右上角加外链入口时把它放在 `#hud` 里 → 开始页浮层（`z-index:20`）把它盖住了，
    hover 不到、点不着。原因不是 `#topLinks` 的 `z-index` 不够（设到 26 都没用），
    而是 **`#hud` 自身有 `z-index:5`，形成了层叠上下文** ——
    子元素的 `z-index` 只在这个上下文内部比较，跳不出去。
    **解法**：把 `#topLinks` 移到 `#hud` **之外**（作为 `#stage` 的直接子节点）再给 `z-index:26`。
    回归里用 `HTML.indexOf('<div id="topLinks">') < HTML.indexOf('<div id="hud">')`
    钉死这个位置关系 —— 这类问题肉眼看代码很容易漏。

24. **测试桩 `localStorage` 是「无操作」的，等于持久化逻辑从来没被测过。**
    `_smoke.js` 原来的桩是 `{ getItem: () => null, setItem() {} }` —— 写进去读不回来。
    后果：纪录写错、脏数据崩溃、上限算错、迁移失效，这套桩一个都发现不了。
    换成 `Map` 支撑的内存实现后，读写往返、容错、迁移才谈得上验证。
    **通用教训**：桩如果「静默成功」，就是在给假绿发通行证；会写入的桩必须真的存下来。

25. **断言读错属性：`innerHTML` 写的，用 `textContent` 读恒为空。**
    `renderGap` / `renderFailBreakdown` 用 `innerHTML` 渲染（内容含 `<b>` 强调标签），
    断言却读 `textContent` → 永远拿到空串 → 测试红、而代码其实是对的。
    **排版用哪个属性写，断言就用哪个读。**

26. **关键词计数要小心前缀重合。**
    验「开始页有两张模式卡片」时，正则 `/class="modeCard[^"]*"/` 把容器
    `class="modeCards"` 也数了进去，得到 3。改成匹配 `id="modePractice"` /
    `id="modeChallenge"` 才准。凡涉及「恰好 N 个」的断言，都要确认模式没有
    意外匹配到相邻名字。

27. **批量改脚本路径时，插入点不能按行号猜。**
    把 `_tools/` 迁移的定位常量插到「前 16 行里最后一个 `require`」之后，
    而 `_phys_perf.js` 的第 11 行正好是**嵌在 `if` 块里**的 `require` ——
    于是 `const ROOT` 被声明在块作用域内，块外的 `readFileSync(ROOT + ...)` 直接
    ReferenceError。**插入点必须取「顶层 require」**（行首 `^const ... require(`）。
    同一次迁移还漏了另一类：`_syntax.js` 的文件清单是手写的，
    脚本搬走后仍在项目根找文件 → 报「文件不存在」。
    **顺手把它改成自动枚举**，以后新增脚本不用再维护清单。

## 已知取舍

- 正手只做基础推挡演出，完整正手动作（攻球、弧圈）未做。
- 反手撕、反手弹击列为扩展；旋转训练模式、慢放观赏、摄像头手势识别、Electron 打包均未做。
- 最高难度档旋转倍率 1.49，此时侧旋球的补偿量要求很精确，失误率明显上升——这是刻意的难度顶点。
- 放慢 40% 后**旋转球**的补偿窗口也变宽（同样时间能看到更多拐弯），
  侧旋的「看弧线判断」难度实际下降；难度顶点主要落在旋转倍率而非速度上。
- 海报只在**破纪录**时自动弹；未破纪录时结算页仍有「分享海报」按钮，但本局没抓到落台瞬间就隐藏。
- 抓帧是「换机位**离屏**补渲染一帧」（独立渲染器，不闪主画面），不是录制回放；
  因此高光三连拍记录的是**落台那一刻的场景状态**
  （球在对方台面上），不是一段动画。
- 海报导出用 `toBlob` 下载，移动端浏览器可能拦截；桌面端正常。
